# EVAL_GUIDE

평가셋 30건. 개선 전후를 같은 셋으로 비교한다.

## 구성

정상 9, 경계 12, 실패 유도 9.

## 정답 만드는 규칙

- 입력과 정답을 LLM으로 만들지 않는다. 사람이 쓴다. LLM이 만든 정답으로 LLM을 평가하면 아무것도 증명되지 않는다
- 경계 문항은 실제로 겪은 상황으로만 만든다. 지어낸 상황은 지어낸 답을 부른다
- 정답을 한 번에 못 정한 문항은 지우지 않고 기록한다 (EVAL_REPORT.md 1절 "판정이 흔들린 기록")
- `why` 칸에 왜 이 답이 맞다고 봤는지 적는다

## 시점

모델을 손대기 전에 만든다. 나중에 만들면 이미 튜닝된 결과에 맞춰진다.

## 평가 축

슬롯 정확도, 도구 선택 정확도, 규칙 판정 정확도(코드), 실제 적합성(사람, 필요 시 judge 보조), 계약 준수율.
축을 나누는 이유는 하나로 뭉개면 무엇이 무너졌는지 안 보이기 때문이다.

judge 모델은 생성 모델과 다른 회사 것을 쓴다 (docs/SDD.md 8절).

## 경로 API는 시각에 따라 값이 변한다

소요시간 절댓값이 아니라 후보 순위와 규칙 적용 여부로 판정한다. 변동 폭을 기록한다.

## 문항 형식

한 줄에 하나. `input` 과 `why` 는 사람이 쓴다.

```json
{"id": 1,
 "input": "토요일 오후 2시 강남역 근처에서 봅시다. 저는 수원시청에서 차로 갑니다.",
 "expected": {"stage": "done", "slots": {"preset": "meeting"}},
 "note": "정상", "why": "절차 이야기가 없고 그냥 만나는 자리라 meeting 이다"}
```

`expected` 는 세 가지로 쓸 수 있다.

| 쓰는 법 | 채점 |
|---|---|
| 비워 둠 (`""`) | 점수를 매기지 않는다. 계약·지연·비용만 잰다 |
| `"done"` 처럼 문자열 | 끝난 단계만 본다 |
| `{"stage": ..., "slots": {...}}` | 단계와 적은 슬롯 칸을 본다. `"access.required"` 처럼 점으로 안쪽 값도 지목한다 |

정답을 못 정한 문항은 `expected` 를 비워 두고 돌려만 본다. 지우지 않는다.

## 실행

```
python evals/run_eval.py --dataset evals/dataset.jsonl
```

결과는 Langfuse Dataset에 score로 남고, 요약을 EVAL_REPORT.md에 적는다.
