# EVAL_GUIDE

회귀셋 10건. 모델을 바꿀 때마다 같은 셋으로 돌려 조용히 나빠지는 것을 잡는다.

30건짜리 평가 리포트를 만들자는 게 아니다. 소형 모델을 재학습하거나 프롬프트를 고치면
전에 되던 것이 안 되기 시작하는데, 손으로 몇 문장 넣어 보는 방식으로는 그걸 못 잡는다.

## 구성

갈래마다 한 건씩. 겹치게 늘리지 않는다. 열 건이면 2분 안에 끝나고, 그래서 자주 돌리게 된다.

| # | 문항 | 보는 것 |
|---|---|---|
| 1 | 일반 약속 | preset=meeting, 절차 소요 없음 |
| 2 | 절차 있는 방문 | preset=visit, 신청 여부까지 |
| 3 | 절차 단서 없음 | access 를 비우고 되묻는가 |
| 4 | 신청 여부 모름 | missing 에 access.applied |
| 5 | 픽업 | pickup 과 pickup_at 이 짝인가 |
| 6 | 시각 없음 | need_info 로 빠지는가 |
| 7 | 이동수단 없음 | missing 에 transport |
| 8 | 성·직함이 붙은 이름 | 이름을 줄이지 않는가 |
| 9 | 짧은 반말 | 형식이 없어도 뽑는가 |
| 10 | 범위 밖 | out_of_scope 로 끝나는가 |

## 문항 형식

한 줄에 하나. `input` 과 `why` 는 사람이 쓴다.

```json
{"id": 1,
 "input": "토요일 오후 2시 강남역 근처에서 봅시다. 저는 수원시청에서 차로 갑니다.",
 "expected": {"stage": "done", "slots": {"preset": "meeting"}},
 "note": "일반 약속", "why": "절차 이야기가 없고 그냥 만나는 자리라 meeting 이다"}
```

`expected` 는 세 가지로 쓴다.

| 쓰는 법 | 채점 |
|---|---|
| 비워 둠 (`""`) | 점수를 매기지 않는다. 계약·지연·비용만 잰다 |
| `"done"` 처럼 문자열 | 끝난 단계만 본다 |
| `{"stage": ..., "slots": {...}}` | 단계와 적은 슬롯 칸을 본다. `"access.required"` 처럼 점으로 안쪽 값도 지목한다 |

## 정답을 정하는 규칙

- 기대값은 "이렇게 나와야 한다"를 적는다. 지금 모델이 내는 값을 베껴 적지 않는다.
  그러면 회귀를 못 잡고 현재 상태를 굳히기만 한다
- 정답을 못 정한 문항은 `expected` 를 비워 두고 돌려만 본다. 지우지 않는다
- `why` 에 왜 그 답이 맞는지 적는다. 나중에 판단이 흔들릴 때 근거가 된다

## 평가 축

단계 도달, 슬롯 정확도, 계약 준수율, 지연, 비용. 다섯을 따로 본다.
하나로 뭉치면 점수가 떨어져도 어디가 무너졌는지 안 보인다.

실제로 쓸 만한 답인지(사람이 보기에 납득되는 집결지인지)는 숫자로 재지 않는다. 사람이 본다.

## 실행

```
python evals/run_eval.py                 # 전체
python evals/run_eval.py --dry-run       # 모델을 부르지 않고 문항만 확인
python evals/run_eval.py --limit 3       # 앞 세 건만
```

결과는 `evals/results/<시각>.json` 에 남는다. 기준선과 비교할 때 그 파일을 본다.

## 경로 API 는 시각에 따라 값이 변한다

소요시간 절댓값이 아니라 단계·슬롯·계약으로 판정한다. 지연과 비용은 참고로만 본다.
